# Project Context

## Purpose

This project is an AI-assisted short video account strategy and content creation system. It helps small businesses, short video operators, and production teams turn a project profile into account positioning, account packaging, execution plans, topic ideas, shooting-ready scripts, and generation history.

The MVP flow is:

1. Create a project profile.
2. Generate an account packaging strategy from that profile.
3. Use the saved account strategy context to generate a 30-day execution plan.
4. Generate short video topics.
5. Generate scripts from selected topics.
6. Review and copy saved generation records.

The current codebase already contains the project profile module and the account packaging generation path. Later OpenSpec changes should continue the Sprint order in `docs/TASKS.md`: LLM Gateway, account packaging, execution plan, topics, scripts, and generation history.

## Tech Stack

### Frontend

- Vue 3 with TypeScript and Vite.
- Vue Router for page routing.
- Pinia is part of the intended stack, although current state is mostly page-local.
- Element Plus for UI controls and feedback.
- Axios for HTTP calls through `frontend/src/api/client.ts`.

### Backend

- Python 3.11+.
- FastAPI application in `backend/app/main.py`.
- SQLAlchemy 2.x models and sessions.
- Pydantic v2 schemas.
- Alembic is part of the intended stack, but the current app initializes tables with `Base.metadata.create_all()` during FastAPI lifespan startup.
- PostgreSQL is the target production database. Local development defaults to SQLite via `DATABASE_URL=sqlite:///./jsvoc_dev.db`.

### AI Layer

- All AI generation must go through `backend/app/llm/llm_gateway.py`.
- Supported providers in the current code are `mock` and `openai_compatible`.
- LLM configuration is environment-driven:
  - `LLM_PROVIDER`
  - `LLM_BASE_URL`
  - `LLM_API_KEY`
  - `LLM_MODEL`
- Generation calls should persist `generation_records` with input, output, provider, model, prompt version, token usage, latency, project id, and optional user id.

## Architecture

The main request flow is:

`Vue 3 frontend -> FastAPI router -> service layer -> prompt builder -> LLMGateway -> provider -> SQLAlchemy persistence -> API response`

Backend directory responsibilities:

- `backend/app/api`: FastAPI routers and HTTP response shaping.
- `backend/app/core`: configuration and environment settings.
- `backend/app/db`: SQLAlchemy base, engine, sessions, and dependency wiring.
- `backend/app/models`: SQLAlchemy table models.
- `backend/app/schemas`: Pydantic request and response schemas.
- `backend/app/services`: database operations and business persistence helpers.
- `backend/app/prompts`: module-specific prompt builders and output schemas.
- `backend/app/llm`: provider abstraction and generation record integration.

Frontend directory responsibilities:

- `frontend/src/router`: route definitions.
- `frontend/src/views`: page-level Vue components.
- `frontend/src/api`: typed API wrappers around Axios.
- `frontend/src/style.css`: shared application styling.

## Data Model Notes

- JSON-like fields should use `JSON().with_variant(JSONB(), "postgresql")` so SQLite local development and PostgreSQL deployment both work.
- Project profile fields include project name, industry, sub-industry, product/service, personal intro, target audience, platforms, current stage, optional user id, and timestamps.
- Account strategy context stores the reusable downstream strategy payload generated by the account packaging module.
- Generation records are the audit trail for all AI outputs and should be created for every AI generation attempt handled by `LLMGateway`.

## API Conventions

- Most business endpoints return:

```json
{"success": true, "data": {}, "message": ""}
```

- Error responses currently rely on FastAPI `HTTPException`; keep messages user-readable and Chinese where they are user-facing.
- Request and response payloads use snake_case to match backend schemas and existing frontend API types.
- Add API wrappers in `frontend/src/api` for new endpoints before wiring page components.

## Development Conventions

- Read the core docs before implementation work:
  - `docs/PRD.md`
  - `docs/ARCHITECTURE.md`
  - `docs/API_SPEC.md`
  - `docs/DB_SCHEMA.md`
  - `docs/TASKS.md`
  - `docs/ACCEPTANCE.md`
- Follow `docs/TASKS.md` by Sprint when planning changes.
- Keep OpenSpec changes scoped to one clear capability or Sprint slice.
- Prefer existing backend patterns: router validates HTTP concerns, service owns persistence, prompt module builds AI prompts, `LLMGateway` handles provider execution and generation record creation.
- Do not call model providers directly from routers, services, or frontend code.
- For new generated modules, define prompt constants, output schema, and prompt builder in `backend/app/prompts`.
- Normalize AI output before persisting or returning it, because OpenAI-compatible providers may return malformed or partially structured content.
- Keep frontend pages operational and direct; this is an internal operations tool, not a marketing site.

## Quality Gates

For backend changes:

- Import-time errors must be absent.
- FastAPI app should start successfully.
- Relevant API routes should be exercised manually or with tests.
- AI generation changes must be verified with `LLM_PROVIDER=mock` at minimum.

For frontend changes:

- `npm run build` should pass.
- Affected routes should be opened in the browser and checked for empty states, loading states, error messages, and successful API calls when possible.

For OpenSpec changes:

- Proposal, tasks, and delta specs should be created under `openspec/changes/{change-id}/`.
- Implementation tasks should be checked off as work is completed.
- Archive only after implementation and quality gates are complete.
